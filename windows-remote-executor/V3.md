# Windows Remote Executor V3

V3 is the preferred control plane for the native executor after a target passes
the V3 acceptance matrix. V2 `invoke-b64` remains available as an explicit
rollback/compatibility route, but new executor deployments do not need to preserve
older fallback behavior once V3 is proven on the target.

## Stability Boundary

V2 reduced local quoting failures by sending one base64url JSON envelope to the
native executor, but the transport still builds a remote `cmd.exe /s /c` command
with user-shaped data in argv. V3 keeps the remote command fixed:

```text
WindowsRemoteExecutor.Native.exe rpc-stdio
```

The client sends one UTF-8 JSON request line on stdin. The native executor writes
one UTF-8 JSON response line on stdout. User payload does not travel in local
argv, remote argv, or shell-authored command text.

## Request

```json
{
  "id": "req-001",
  "action": "process.capture",
  "timeoutSeconds": 30,
  "captureLimitBytes": 1048576,
  "accessToken": "optional plain policy token",
  "payload": {
    "file": "whoami.exe",
    "args": []
  }
}
```

Fields:

- `id`: caller-provided correlation id.
- `action`: one supported action name.
- `timeoutSeconds`: reserved request timeout field. The initial native scope does
  not enforce process termination yet; the Python transport uses it as an SSH
  timeout plus margin.
- `captureLimitBytes`: reserved capture limit field. `file.readText` enforces
  `payload.maxBytes`; broad stdout/stderr truncation is deferred.
- `accessToken`: optional plain token checked against `access-policy.json`.
- `payload`: action-specific object.

## Response

```json
{
  "id": "req-001",
  "ok": true,
  "exitCode": 0,
  "errorClass": "",
  "stdoutText": "...",
  "stderrText": "...",
  "stdoutEncoding": "utf-8",
  "stderrEncoding": "utf-8",
  "stdoutBase64": "...",
  "stderrBase64": "...",
  "stdoutBytes": 3,
  "stderrBytes": 0,
  "startedAt": "2026-06-29T00:00:00.0000000+00:00",
  "endedAt": "2026-06-29T00:00:00.0100000+00:00",
  "durationMs": 10,
  "data": {},
  "evidence": ["ProcessRunner.RunCaptureAsync"]
}
```

`ok` is false for transport-level validation failures and for captured processes
that return a non-zero exit code. `errorClass` is intended for routing retries:
`protocol`, `auth`, `unsupported`, `path-shape`, `request`, `remote-process`, or
`remote-exception`.

## Actions

### `host.capabilities`

Payload: `{}`

Returns supported protocol metadata in `data`:

```json
{
  "protocol": "wre-rpc-stdio",
  "version": 3,
  "actions": [
    "host.capabilities",
    "host.probe",
    "process.capture",
    "script.capture",
    "file.writeText",
    "file.readText"
  ]
}
```

### `host.probe`

Payload: `{}`

Runs the existing native `ProbeCollector.Collect` path. `data` contains the probe
object and `stdoutText` contains the same object as JSON plus a trailing newline.

### `process.capture`

Payload:

```json
{
  "file": "whoami.exe",
  "cwd": "C:/CodexRemote/inbox",
  "args": ["/all"]
}
```

Runs a native Windows process through `ProcessStartInfo.ArgumentList`; no shell is
used for the child process. `file` is policy-checked the same way as V2
`capture-b64`. The Python client preserves the V2 raw PowerShell guard: direct
`powershell.exe` / `pwsh` capture is blocked by default and should use
`script.capture` or staged exec unless an explicit escape hatch is provided.
Drive-relative path shapes such as `D:tool.exe` are rejected by the Python client
and native path policy where applicable.

### `script.capture`

Payload:

```json
{
  "kind": "powershell",
  "script": "$PSVersionTable.PSVersion.ToString()",
  "cwd": "C:/CodexRemote/inbox",
  "exe": "powershell.exe"
}
```

`kind` may be `powershell`/`ps` or `cmd`/`batch`. The native executor writes the
script body to a temporary UTF-8 file and runs PowerShell with `-File` or `cmd.exe
/d /s /c <temp-file>`. This preserves script text outside argv and avoids local
shell quoting. The temporary file is deleted best-effort after capture.

### `file.writeText`

Payload:

```json
{
  "path": "C:/CodexRemote/inbox/hello.txt",
  "text": "hello\n"
}
```

Writes UTF-8 without BOM, creates the parent directory if needed, and returns a
file proof in `data`: path, byte length, SHA-256, and last write time UTC.

### `file.readText`

Payload:

```json
{
  "path": "C:/CodexRemote/inbox/hello.txt",
  "maxBytes": 1048576
}
```

Reads the file bytes, decodes with the existing output decoder, returns text and
base64 bytes, and returns the same file proof in `data`. If `maxBytes` is set and
the file is larger, the request fails before reading the file.

## Python Client

The client module is `windows-remote-executor/lib/wre_v3_client.py`. It loads the
same target model as `win_remote_cli.py`, resolves the current native executor,
checks help output for `rpc-stdio`, then sends the JSON request on SSH stdin.

Typical imported use:

```python
import win_remote_cli as cli
import wre_v3_client as v3

target = cli.load_target("X570")
call = v3.process_capture(target, "whoami.exe")
print(call.response["stdoutText"])
```

For MCP, V3 should be called through this module rather than by running
`subprocess.run([win-remote, ...])`. V3-covered MCP tools default to this route;
set `WIN_REMOTE_MCP_TRANSPORT=legacy` or `WIN_REMOTE_MCP_TRANSPORT=v2` only for
rollback or older targets that have not passed the V3 matrix.

## Deployment Rule

1. Build and publish the native executor as the normal GitHub release asset.
2. Deploy that asset to X570 with existing `update-tools`.
3. Run the explicit V3 matrix.
4. When V3 passes, switch V3-covered MCP tools to the default V3 route.
5. Keep V2/legacy only as an explicit rollback or older-target route; historical
   V2 fallback tests are useful diagnostics but no longer block final V3-first
   deployment.

For a new desktop-only Windows machine, create a manual administrator bootstrap
package first with `scripts/make-bootstrap-package.sh`. Prefer the self-contained
`scd-win-x64` release asset for a brand-new host so the native executor does not
require a separate .NET 8 runtime install; the framework-dependent `fdd-win-x64`
asset is also accepted when .NET 8 is already present. This `scd` preference is
scoped to the bootstrap package only; X570 `update-tools` still uses `fdd-win-x64`.
Remote V3 validation waits until the user runs that package and reports target
connection details.
